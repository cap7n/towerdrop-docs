    • 2026-08-15 Captn finished Server-side storage for skill-tree tool data (task #124)
      • Did: tool_state table, GET/PUT /tool-state, compare-and-swap, 409 on version mismatch, sync pill red, tool stops pushing, localStorage fallback, tool reads team key from tasks.cfg, npm run smoke passes with 9 assertions, correct URL, key header, body fields, 409 path
      • The plan said: Server-side storage for skill-tree tool data. Move the skill-tree maker off file:// localStorage onto the server so the team shares one canvas instead of one private copy each. Shape: a tool_state table (key, json, updated_at, updated_by) following the existing PRAGMA table_info migration pattern in db.js; GET/PUT routes behind X-Team-Key like every other API route; and a smoke.js case (house rule: a server feature adds a smoke case). Living in tasks.db means db.backup() and the 04:00 nightly cover it for free - do NOT invent a side file, and never cp the db. THE REAL DESIGN ISSUE IS CONCURRENT EDITS. localStorage was single-user by accident. Two people with the tool open will clobber each other: last write wins, no warning, and a tree is an afternoon of work. The board itself dodges this because every write is a small scoped mutation, whereas a tree save is the WHOLE document. Minimum honest fix, and it has to be there from day one rather than added after the first lost afternoon: optimistic concurrency. Client sends the version it loaded, server 409s if it moved, tool says someone else saved - reload. Same shape as any compare-and-swap. Tool side: save() and load() swap localStorage for fetch, keeping a localStorage fallback so the tool still works offline on one machine. Independent of the Tools button task - the button can ship first with the tool still on localStorage (each teammate gets a private canvas: useless for collaboration, but it proves the plumbing)
